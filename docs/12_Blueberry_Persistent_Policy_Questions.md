# 下一步：蓝莓持续供水策略的待确认信息

状态：业务澄清清单。此轮主工作台已为后续方向保留接口边界，以下功能尚未实施。业务假设不能直接当作已校准农艺知识。

## 第一组：需要先由产品／农艺负责人确定

| 问题 | 需要的答案 | 影响 |
| --- | --- | --- |
| 主生产场景是什么？ | 基质盆栽＋避雨设施，或土壤露地；若两者都要，先选一个首发场景 | 根区储水、排水、有效降雨、传感器变量与操作方式 |
| 首轮训练覆盖哪个真实生产阶段／时间跨度？ | 例如选定果实膨大至采收的一段管理窗口；明确是否有不同批次 | 不把 28 天训练误写成多年生蓝莓完整生命周期；确定阶段目标和阶段复核 |
| 设备能做哪些自动调整？ | 定时程序＋人工抽测，或具有传感器反馈的控制器；谁执行和维护 | 策略授权范围，自动执行频率，异常是否只能次日处理 |
| 玩家选择持续策略的粒度？ | 单个生产单元、实际灌溉区、可批量设置；同区是否共用阀门与水肥控制 | 策略目标和设备能力应一致，不能对不可独立控制的单元承诺独立策略 |
| 经理首先优化什么？ | 稳定商品果产量／品质、长期植株健康等；水量、预算、劳动约束优先级 | 不以“水分胁迫为零”作为单一优胜目标 |
| 异常发生时的授权边界？ | 控制器允许自动维持／减量到什么程度，何时停止并报告；早会闭环是否保持 | 系统不越权，也不要求玩家处理每一次滴灌 |

## 第二组：可提供实务样例，也可共同采用明确标注的训练参数

优先提供一份典型正常日和一份异常日的记录，不需要一开始准备完整科研模型。

- 品种／株龄、栽培介质或土壤、盆体或有效根区、种植密度、设施和排水条件。
- 实际生育阶段、典型供水方向、晴天／阴天的调整思路和复核条件。
- 灌溉区与生产单元关系、控制器模式、滴灌送达范围、设备故障影响范围。
- 常规可获得的信息：含水率／人工湿度判断、供液量、排液量／比例、EC、pH；每项的对象、单位、采样时间、送达延迟、可靠性。
- 两三个优先异常：持续偏干、持续偏湿、末端堵塞／送达不足；哪些现象只能作为症状，哪些证据足够触发调整。
- 调整／维修／人工补水的人工和水量成本、恢复延迟、副作用、后续复查方法。
- 哪些阈值有基地实务依据，哪些允许先用训练参数。没有数据的变量保留未测／未知，不填虚构精确值。

## 实现前必须写清的最小契约

| 契约 | 至少包含 |
| --- | --- |
| 变量定义 | ID、对象范围、类型、单位、有效范围、缺失状态；区分测量、估计、风险、概率、严重度和可信度 |
| 观测记录 | 地块／作物批次／设备等明确对象、变量、值、来源、observedAt、availableAt、可靠性和误差 |
| 持续策略 | 独立 ID、对象、版本、生效时间、阶段目标、供水方向、设备权限、复核／失效条件 |
| 措施定义 | 前提、能力要求、资源需求、效果范围、时间延迟、副作用、效果验证条件 |
| 日内执行 | 固定且可回放的更新顺序、水量平衡、送达与消耗、干湿持续后果；不向 UI 暴露隐藏真值 |
| 经营与复盘 | 本次选择的目标及硬约束、预计与实际用量、偏差原因、哪些结果仍需观测验证 |

供水调整与营养调整是独立选择。第一版可以维持少量阶段营养模板，不引入自由配肥与施工。基本设备不具备的自动能力不能由 UI 默认获得。

推荐验收：“正常日比当前更少重复点击，异常日的证据与取舍更清楚；玩家能解释调整原因”。同场景同命令可重复，新增模块不得意外改变天气抽样；涉及随机流或存档版本变化时需要独立回放和迁移验证。
