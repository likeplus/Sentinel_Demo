# Phase 2 农场经理试玩流程优化设计

日期：2026-10-08。基线：main 的 `236983471be02c82b991d26f50f492b36dd7ca1c`。开发分支：`feature/manager-flow-batch`，提交到 main 的 PR，合并后才由 GitHub Pages 发布。

## 设计目的

本轮承接 Phase 2 的试玩反馈，帮助农场经理更快完成“看情况 → 选单元 → 安排 → 执行 → 看结果 → 次日重排”。沿用已有生产单元、地图、蓝莓内容、三个场景决策、资源与经济参数、延迟汇报、委派审批、传感器和季末五维复盘，没有重做游戏或增加新的经营系统。

原试玩方案存档见 [修改前试玩与建议](design/Phase2_Manager_UX_Proposal_2026-10-08.md)。本文描述实施后的行为，供团队后续修改设计使用。

## 每日流程

新会话默认进入“今日工作”，先呈现待处理场景、天气、可用资源、已知风险和信息缺口。水分风险、可信度、新鲜度各自显示，未知信息仍为未知；这里的优先事项只使用玩家已经获得的信息。

今日任务单独列出，未来任务与送达报告可展开。报告标明生产单元，水分数值统一为 0–100。已完成任务与历史默认折叠，避免经营后期把当前决策推到长页面底部。

```mermaid
flowchart LR
  M[早会：观察与排程] -->|开始执行| E[执行当天作业]
  E --> R[自动停在日终结果]
  R -->|玩家点击次日早会| N[更新天气与有效观测]
  N --> M
```

内部三阶段接口保留；界面在一次“开始执行”操作中调用执行及日终两个步骤，日期不前进，不重新开放排程。第二次点击才进入次日。28 天固定推进由 84 次减少至 56 次。经理注意力的定义及收费保持：早会 1、普通排程 0、复杂经理判断 1、每单元经理巡查 2。

## 选择与就地排程

表格行有明确复选框，表格下方另有生产单元选择区；卡片与地图也有可点击、可键盘操作的多选入口。查看单元详情和加入操作组是两件事：编号打开详情，复选框改变操作组。

表格、卡片、地图共用同一组选中单元，切换页面或视图不会覆盖选择。筛选条件改变后，只保留仍然可见的单元并更新数量。多选摘要保留每个单元自己的风险、可信度与新鲜度，不合成总分。选择是本次打开页面的界面状态；刷新可恢复经营进度，但不恢复多选组。

点击“安排所选单元”后，在原页面显示任务表单。单元详情、今日风险入口也打开同一表单并预选单元、今天及对应动作；普通任务不用跳去另一个页面重填。采购使用原有付款确认对话框，关闭后原表单参数仍在。

### 批量排程的规则

1. 日期、动作、班组及巡查附加措施填写一次。每个单元生成一条独立任务、决策依据和结果链。
2. 报价汇总人力点、注意力、用水、费用与人员日；校验该日期已有预约、指定班组及设备、未来水量预留和现金。
3. 任一重复或资源冲突时，整批不提交；明确显示相关单元、已有任务和资源限制。没有静默跳过或部分成功。
4. 重复检查包含组合动作，经理巡查与班组巡查共享巡查唯一性。同单元、日期和动作仍只允许一次。
5. 移动传感器只能迁往一个目标；多选迁移被阻止，并提示逐项安排。
6. 成功后展示每个单元的日期、动作和资源，提交按钮锁定，直到用户改变计划参数。引擎请求编号进一步防止同一请求重复创建任务。
7. 查看重复或已创建任务采用应用内导航并定位、高亮对应任务。GitHub Pages 的 `#/game` 路由不会被任务锚点替换。

## 决策、资源与反馈

复杂问题的团队委派保留一个入口；普通单元隐藏不适用的复杂委派入口，界面与引擎共用分类规则。注意力用完依然允许团队与助手建议。场景汇报保留原来的送达日期；即时单元建议直接定位到接受/拒绝卡片。助手不提供修改建议。

接受建议前展示实际报价。标准任务与原场景完整方案可以有不同持续时间和覆盖范围；保留原参数，解释人员日与人力点换算，使用引擎已有排程检查来报价，不以显示文本里的估计费用代替实际资源计算。

日终结果显示单元、动作、完成或受阻、人力、用水及发生费用。巡查分别列出作物与设备发现，报告与行动仍独立保存。补水的当天预计影响与次日正式估计、最新观测的数值/来源/时间/可信度分别标示，避免把预测当作实测。

作业页先列待执行、受阻任务，日历、传感器、完成和取消历史默认折叠。季末日历默认显示最后七个经营日（03-22～03-28）；季末不显示可提交的任务表单。经理理由可选，未填写不再表现为未完成步骤。

## 信息新鲜度的可读表达

根据最新试玩反馈，统一名称为“信息新鲜度”。数值显示“当天／N天前／暂无信息”，英文对应 Today／N days ago／No information yet，不再使用 0d、5d+ 或“作物 4天”这样的缩写。

表格与单元详情分别显示“水分信息更新”和“作物与设备信息更新”。例如：水分信息更新：当天；作物与设备信息更新：4天前。旁边解释这表示获得有效信息的时间，不是作物年龄；经用户确认：一次有效巡查同步更新水分、作物与设备信息，巡查后日期一致；之后允许传感器单独刷新水分信息，所以两类日期可能不同。保留真实天数，风险和可信度不随文案改动合并或重算。玩法简介中新增独立说明卡，使用“昨天巡查、今天传感器更新”的例子解释两类更新时间和来源，可继续按模块扩展。

## 单位、语言与存档

中文容量、价格、提示、结果与复盘使用“立方米”；英文使用 `m³`。面积中文为“公顷”，雨量与蒸散中文为“毫米”。数字比例及路径分隔符 `/` 保留，不再被翻译成“月”；`m` 不会再匹配经理头像的 `M` 而成为“农”。所有改变仅作用于显示，不改变数值、ID 或存储单位。顶部中英切换与原 Demo 的语言偏好继续共用。

自动存档原先只复用观测；历史快照中的重复任务、决策和其他对象仍反复序列化。本轮使用完整 JSON 对象池复用相同数据，保留全部经营状态、历史日期与随机状态。旧 `observation-pool-v1` 存档仍可读取，下一次成功保存转换为 `object-pool-v2`；内容版本与存档键保持兼容。损坏及不兼容存档仍保留原值，真实写入失败仍显示风险提示，不伪称已保存。

## 实现入口及后续扩展

| 文件 | 责任 |
| --- | --- |
| `src/game/GameApp.jsx` | 今日工作、跨视图选择、就地入口、导航定位、场景建议报价 |
| `src/game/FeedbackViews.jsx` | 共用排程表单、选择区、日历、建议历史、日终反馈 |
| `src/game/FarmMap.jsx` | 地图多选与原空间交互 |
| `src/game/GameController.js` | 两步界面推进、只读报价缓存、批量提交 |
| `src/simulation/SimulationEngine.js` | 在状态副本上预检整批，全部成功后原子提交；沿用原场景方案预检 |
| `src/simulation/FarmManagement.js` | 原单任务规则、复杂判断分类、受阻反馈 |
| `src/game/persistence.js` | 完整对象池编码、兼容旧编码、损坏索引校验 |
| `src/game/localization.js`、`gameText.js` | 语言与单位显示 |
| `src/game/content/gameplayGuide.js`、`cropKnowledge.js` | 模块化玩法说明与作物百科；继续按模块/卡片扩展 |

增加动作时维护 `FARM_ACTIONS`、执行结果、资源约束和双语名称；批量层自动沿用每个单任务的检查。场景多单元共享方案与“每单元各做一次”的批量普通任务是不同语义，不能把共享用水方案直接乘以单元数。角色能力接口继续保留，不扩大农场经理的固有现场权限。

## 验收与边界

见 [本轮验收记录](validation/manager-flow-results.md)。验收覆盖批量的成功、重复、资源失败、全量撤回、请求重试、经理注意力、移动传感器，以及高频巡查下 28 天的实际浏览器存档/刷新恢复。旧场景和原 Demo 路由继续回归。

浏览器存储仍受网站配额与设备限制。本轮验证 28 天、112 次任务并保留 29 个历史日期；没有声称无限历史永远不超配额。当前助手继续是本地规则生成的建议，未接入新的外部 AI 服务。

## 2026-10-09 试玩反馈补充

在本流程上新增阶段知识直接定位与共用名称、日终执行结果表格、温度一位小数，并移除待处理决策里的重复资源摘要。后续设计见 [10 阶段知识与日终复盘](10_Phase2_Review_Clarity_Design.md)。
