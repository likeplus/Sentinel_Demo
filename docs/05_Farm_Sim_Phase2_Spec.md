## 2. 下一阶段目标

玩家固定扮演 Farm Manager。在浏览器中以农场地图为入口，完成云南蓝莓场景的 28 个每日推进，并体验：

观察 → 理解证据与不同观点 → 调查 / 决策 / 委派 / 等待 → 排程 → 执行 → 后果 → 复盘。

28 天、12 个 PU、3 个 cluster、3 个品种均为首个内容包配置，不得成为渲染或模拟引擎中的常量。保持现有 Demo 和九条路由，新增 Game 入口；不整体替换旧 Zustand store。

## 4. 不能直接靠 UI 接线解决的缺口

### 4.1 地图阶段、风险与信息边界

当前 `getPlayerView()` 不暴露作物真实阶段、真实胁迫或产量/品质潜力。现有 Observation 仅允许数值。设计需要阶段图标，因此要设计玩家可获得的阶段报告或带依据的估计接口，并对已有数值观测保持兼容。

地图风险依据当前可用观测/Belief 计算；标明“观测”或“估计”、来源、置信度及时间。没有证据显示 unknown，过期信息保留最后已知值并显示灰雾/stale。风险新鲜度按对应变量判断，不能因为同一 PU 收到另一种报告就把所有指标标记为最新。

报告须同时满足 `observedAt` 与 `availableAt` 的时间门槛。计划时间线只显示玩家已知的作业、预期窗口和通知，不展示实际未来事件、尚未送达报告或未来执行结果。

### 4.2 Manager Attention

第二份设计将 Manager Attention 定义为正式资源，当前代码尚未实现。建议本阶段加入可配置的每日预算与行动成本，HUD 展示剩余额度；推进一天按配置恢复。调查、亲自决策和委派的消耗规则明确，成本在接受行动时原子扣除，冲突拒绝和重复提交不得重复扣费。

初始数值作为内容配置并通过试玩调节，无需用户现在指定精确点数。

### 4.3 决策、调查、委派与期限

当前灌溉和检查流程已经可执行；`delegate` 只记录委派对象和状态，尚未驱动下属执行。采收前 case 缺少实际行动方案。delay 的期限、提醒及再决策规则也需要明确。

建议至少形成三个可完整体验的决策节点：观测冲突、设备/劳动力干扰中的一个、采收前资源权衡。每个节点具有可用证据、观点、成本和可执行选项，行动产生可追踪后果。事件继续通过窗口/条件/概率触发，不把整个故事改成固定日历脚本；用于验收的指定 seed 应确实触发所验收节点。

用户已确认先交付 Approval 一档：下属依据其可获得的证据形成建议，经过约定的汇报延迟送达，由经理批准后排程。未经批准不自动执行。定义建议送达、批准/拒绝、Attention 成本和未及时批准时的提醒规则。NPC 建议可由确定性规则生成，不必接外部大模型；不得假装规则输出来自真实在线 AI。

延后时记录复查日期与提醒；明确期限错过后的 case 状态与后果。不行动应保留理由及后续结果，不能在复盘中无依据地标记为“正确”或“错误”。

### 4.4 排程与财务

保留计划/实际分离、库存与容量分别校验、执行时再次检查可用资源。手动改期应释放旧预约并重新校验，不能留下重复预约。

财务将现金、作业成本、预计收入明确分开，预计收入不等于已实现利润。文档提出 emergency purchase：建议以配置化、显式确认的应急补水操作形成现金扣除与库存增加，并保证只记账一次。资金不足、是否允许负现金须形成内容规则；首版建议拒绝资金不足的主动采购，不自动采购。

### 4.5 存档与复盘

用户已确认本地自动存档，刷新可继续；另提供明确的重新开始操作。这是新工作，现阶段没有浏览器持久化。checkpoint 仅用于引擎恢复，包含隐藏状态，不能传给展示组件或用作玩家的决策依据。注明存档版本；不兼容时清楚提示，不静默覆盖。

28 天结束生成多维复盘：财务状况、基于证据的作物状况/预期产出、水资源使用、运营可靠性、决策与审计记录。展示依据、行动和实际结果，不合成一个总分，也不把示例参数包装成科学校准结果。

## 5. 分步实施

1. 先形成安全的 UI 数据接口，补齐阶段/风险展示与 Attention 的规则和测试。
2. 新增 Game 入口、SVG 地图、PU Quick Panel、Today 与逐日推进。
3. 接入 Decisions、调查报告与理由记录，补齐场景节点及选定的委派方式。
4. 接入 Operations、冲突处理、资源与财务、应急采购。
5. 完成存档/重开和结束复盘，再进行 Windows 浏览器试玩及原 Demo 回归。

每一步保持可运行，不以重写所有旧页面为前置条件。针对会被复用的 React Hook 缺陷修复；其他旧 lint 问题单独记录，新代码不得新增问题。浏览器默认每次推进一天；不将 120 天完整模拟放在同一次同步点击中。对推进响应和存档成本做实际测量，发现卡顿后再针对性优化。

## 6. 可检验的完成标准

1. Windows 浏览器能够完成 28 个每日推进；日期边界与引擎语义一致，到终点停止，不多执行一天。
2. 地图从数据生成全部 12 个 PU / 3 个分区 / 3 个品种；通过小型不同 PU 数量 fixture 验证没有硬编码。
3. 点击任意 PU 能追踪至其观测、决策与作业；unknown/stale/current 状态、颜色图例和更新时间清楚。
4. 调整隐藏真值或未送达报告不会改变此前的页面视图；未来回放请求不可用。送达日期到达后报告才出现在 UI。
5. 检查、行动、委派、延后及不行动按照各自规则运行；理由与当时证据可在复盘中追溯。默认验收 seed 跑通约定的完整节点。
6. 劳动力、设备、库存或 Attention 不足时显示具体冲突，拒绝操作不产生部分扣费/预约；执行期资源变化能够阻塞或延迟任务。
7. 计划与实际差异、费用和库存变化可核对，应急采购及重复点击不重复记账。
8. 相同 seed 加相同有序玩家输入产生相同结果；换 seed 不承诺必然出现某一特定事件。存档恢复后保持未来结果一致。
9. 完成多维复盘，明确预测与实际；刷新存档、重开及结束状态均可测试。
10. build、相关模拟/UI测试、原九条 Demo 路由回归通过，lint 不增加诊断；在 Windows 记录一次真实试玩结果。
