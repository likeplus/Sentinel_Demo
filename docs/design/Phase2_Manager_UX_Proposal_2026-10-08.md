# 农场经理视角试玩与流程修改方案

日期：2026-10-08　状态：**仅提出方案，未执行游戏修改**

本次补充：表格下方的生产单元选择入口、跨视图多选与批量排程，以及中文单位统一显示“立方米”。已检查现有实现，以下新增项仍处于方案阶段。

## 1. 试玩范围与结论

通过浏览器中的真实界面，从新存档开始经营完整 28 天：2026-03-01 至 2026-03-28，进入 2026-03-29 的季末复盘。经营选择依据玩家可见的报告、状态表、资源和任务，没有调用隐藏状态或修改经营数据来推进游戏。

试玩对象是 Phase 2 反馈整合后的 GitHub Pages 版本，仓库为 https://github.com/likeplus/Sentinel_Demo ，对应 main 提交 `236983471be02c82b991d26f50f492b36dd7ca1c`。本地 checkout 与该提交的代码树一致。由于当前环境不能访问线上 github.io 域名，本轮使用相同源码的 Pages 构建，在本地静态服务中试玩，保留线上使用的路径前缀和 HashRouter。浏览器为 Chromium，中文，1440 × 960。

这是一次由助手操作界面的经理视角体验审查，不是多位真实玩家的可用性实验，也不是所有功能的穷举验收。已有设计背景不能完全消除，以下优先依据实际操作遇到的阻碍，而不是原设计清单。

**结论：经营闭环可以完成，主要阻碍是信息与操作的位置。** 玩家不断在“今日工作、总览、排程、决策”之间找对应关系；进入中后期，历史记录占据页面，当前问题越来越难找。应先修复流程中断，再减少跳转、重复确认和无新增内容的阶段点击。

保留现有玩法：早会排程、有限劳动力和注意力、风险/可信度/新鲜度分离、巡查组合、灌溉反馈、委派批准、未来任务、完整历史与季末复盘。本方案不增加新的经营系统。

## 3. 修改优先级

### 第一批：先消除中断与误读

| 编号 | 实测问题 | 建议修改 | 验收条件 |
| --- | --- | --- | --- |
| A1 | 03-01 重复创建巡查后，点击“查看 TASK-3”进入 `#operation-TASK-3`，游戏变成空白页 | “查看”定位已有任务卡，保留游戏路由与存档；不要把任务锚点写进页面路由 | Pages 构建下重复任务的查看、改期、取消均能操作，无需重新打开游戏 |
| A2 | 03-16 出现“自动存档失败，刷新可能丢失本次进度”，持续到季末 | 定位失败原因，保证完整经营周期可保存与恢复；失败提示与“刷新会继续进度”的说明一致 | 使用本轮同等规模的正常排程完成 28 天，存档成功；中段及季末重新打开可恢复日期、任务、资源与历史 |
| A3 | 中文界面把水量写成“农³”，注意力写成“3 月 4”，天数写成“第 0 月 28 天”；报告水分值用 0.66，总览用 66/100 | 固定数字、单位和分隔符的格式；中文水量统一显示“立方米”，英文显示“m³”；玩家界面水分值统一采用同一尺度 | 中文显示“3/4”“第 1 天/共 28 天”“20 立方米”，单价显示“¥2/立方米”；报告、总览、趋势和结果中的数值可直接对照 |

A2 的根因尚未证实，不把它直接归因于浏览器容量。本轮没有刷新验证损失范围，以保留完整经营进度。浏览器页面错误列表为空，并不意味着保存成功；界面已经明确报告保存失败。

**A3 补充复查结果与范围：**

只读运行现有文字转换函数，确认 `m³` → `农³`、`20 m³` → `20 农³`，单独的 `/ ` → `月 `；采购数量标题却仍显示 `m³`，说明不同入口的单位呈现并不一致。文字目录将经理头像的 `M` 与“农”建立映射，通用转换不区分大小写，误匹配了立方米符号中的 `m`。这不是只改一个水量标签就能解决的问题。

后续修改应将单位与数字的呈现从普通文字翻译中分开，统一覆盖资源栏、排程容量、任务确认、采购数量与单价、任务结果、报告、提示、场景说明及季末复盘。中文水量使用“立方米”，面积使用“公顷”，降雨和蒸散量使用“毫米”；英文对应 `m³`、`ha`、`mm`。界面栏目中文使用“生产单元”，英文使用“Production Unit”，`PU-01` 等单元编号保留。

验收不仅检查单独词条，还要检查完整句子和拆开的数字/单位片段；中英反复切换后单位、分隔符、数值与单元编号均应正确。该格式调整只影响显示，不改存档中的单位代码、物理数量或计算。

### 第二批：整理每天的主流程

**B1. 早会从“今日工作”开始，把今天要判断的事情摆在前面。**

实际问题：首日“今天需要你关注 0 项”只计待处理的场景决策，但总览有大量未知信息、过期信息。经理容易把“没有决策案件”理解成“今天没有工作”。03-22 的水库调拨说明藏在决策卡里，首页只看到库存为零。

建议在现有今日工作页，按这个顺序呈现：

1. 昨日反馈摘要：对应单元、完成/受阻、关键变化。
2. 今日变化与待处理事项：现有资源变化、待批准建议、已知高风险、信息陈旧/未知。
3. 今日已排程任务及剩余资源；未来任务默认折叠。
4. 全部报告、趋势图和历史，放在需要时展开的位置。

待处理决策数量明确写“待处理决策”，不再代替全部关注事项。提示只使用已经送达、玩家已经知道的信息；不把未知当正常，不替玩家自动排序成唯一正确答案。水库调拨、人手减少等已有事件在早会直接解释变化原因。

验收：不用先切换三个页面，就能知道昨天做了什么、今天发生了什么、已有任务占了多少容量；没有场景决策时仍能识别信息盲区。

**B2. 从问题或生产单元直接打开相应操作，保留上下文。**

实际问题：选择单元后，“安排任务”把玩家送到很长的排程页；页面继承原来的滚动位置，标题、提示与表单可能不在眼前。进入玩法简介时，也曾直接落在页面后半段。

建议保留一个任务表单：在单元面板或报告中打开紧凑的内联表单，预填当前单元、今天和所选动作，资源需求与确认按钮放在一起。未来日期、组合措施仍使用现有字段；完整排程页用于查看多日安排与改期。

巡查快捷入口与普通表单采用同一套默认值、成功提示和资源校验。菜单切换从页首开始；“查看某问题/任务”的跳转直接定位并短暂高亮该对象，而不是继承不相关的滚动位置。

点击目标：从已选中单元完成常见排程，当前通常需要“安排任务→选择作业→确认”，改成“动作入口→核对并确认”。这是设计目标，不是已实现的数据。需要判断日期、组合或资源的步骤仍保留。

验收：玩家始终能看见正在安排哪个单元、哪一天、什么工作；安排后不需要通过返回总览来确认对象。

**B3. 排程成功就地显示具体结果，避免重复确认。**

实际问题：成功提示只有“操作已记录，进度已自动保存”，表单保持原样，确认按钮仍可点击；再次点击得到重复任务报错。

建议在确认处显示“PU-04｜今天｜巡查已排程｜劳动力 1”，同步出现这条任务；同单元、同日期的已排程动作显示明确状态。重复时直接展开已有任务的查看、改期和取消，不让玩家继续猜是否成功。

不增加一次额外“确定”弹窗。常见任务继续一次确认即可。

验收：排程后立即看见具体任务与资源预留；双击/重复点击不会产生第二条任务，也不会进入空白页面。

**B4. 当前任务和待处理决策置顶，历史默认收起。**

实际问题：03-04 决策卡前已经有 11 条排程决策历史；03-22 当前决策的操作按钮在文档约 12,000 像素的位置。季末作业排程页高约 37,888 像素。传感器表、观察日历也挡在任务卡之前。

建议：决策中心先显示待判断、待汇报、待批准的事项，再显示折叠历史；作业排程先显示今天/未来待执行及受阻任务，再显示日历、传感器和已完成/已取消历史。取消、改期留在对应任务行；“保留”作为当前状态，不要求额外点击。

总览与生产单元页面的重复入口可收敛：总览负责全农场状态，单元详情负责所选单元；表格模式下收起只影响空间图的图层按钮。先验证具体重复项，不做整套菜单重建。

验收：历史增加到本轮规模后，当前问题与待执行任务仍在首屏工作区域；回看历史不丢失原记录。

**B5. 执行完成后直接呈现日终反馈，减少一次空转点击。**

实际问题：每一天要点击“开始执行→日终复盘→次日早会”；执行与日终页面的任务结果基本相同，只改了阶段标题。

建议保留内部“早会→执行→日终→次日早会”的规则，但开始执行后自动完成执行并停留在日终结果。玩家查看结果，再主动点击“进入次日早会”。下一天不开自动排程，执行发现的问题仍留到次日处理。

本轮阶段按钮实际点击 84 次；按此方案，同样 28 天应降至 56 次，减少 28 次固定点击。这个预期只适用于阶段推进，不代表所有操作都能减少三分之一。

无作业的日子显示“今天没有安排作业”，直接进入当天总结；不加每天都必须确认的提醒弹窗。

验收：一次“开始执行”后，看见完整的完成/受阻和资源结果；下一天仍由玩家主动进入；不会重新开放当天排程。

**B6. 每条报告和结果，都能回答“哪块地、发生了什么”。**

实际问题：今日报告常只写“水分胁迫、传感器、0.66”，没有单元标识；巡查反馈写任务编号和“可信度 90%”，没有作物/设备发现。灌溉预计变化虽有单元名称，次日摘要仍保留昨日“预计”，正式结果要到总览对照。

建议采用统一结果行：

> PU-03｜系统灌溉完成｜用水 20 立方米，劳动力 1｜执行后预计 66→36；次日最新观测 41，来源传感器，可信度 92%。

这里的数字来自本轮 03-02～03-03 的实际界面。巡查行分别呈现已产生的作物与设备观察、异常及可信度；不能把不同来源、不同时间的数值伪装成确定的实测变化。

每行可展开现有详细记录，并直接查看对应单元或相关任务。已有正常报告按单元归拢，异常/变化优先展示，避免五条没有归属的相似文字。

验收：不切回地图也知道任务影响了哪个单元；预计与正式观测明确区分；观察与行动继续各自保留。

**B7. 表格直接选单元，多个视图共用多选与批量操作。**

现状检查：生产单元总览与农场总览的状态表共用同一个表格组件，单元编号实际上可点击，但只支持单选，表格下方没有明确的选择入口；单元卡片与地图也采用单个选中单元。按本次反馈，应改善入口和选中反馈，并加入批量操作。

建议在生产单元总览表格下方增加明确的“选择生产单元”区域，可直接勾选单元并进行操作，无需先切换地图。表格行有复选框，单元卡片/空间视图也有明显的多选方式，不要求玩家知道 Ctrl 或 Shift 快捷键。

各入口共用同一组已选单元：切换表格、单元卡片或地图时保留选择。点击单元名称用于查看详情，复选框用于加入/移出操作组，避免查看详情时意外覆盖整个多选。改变筛选条件后只保留仍可见的已选单元，立即显示更新后的数量，避免对隐藏单元误操作。

已选区域显示“已选 N 个生产单元”、单元编号、清空选择和“安排任务”。多选后，右侧显示选择摘要及总资源需求；各单元的风险、可信度、新鲜度仍独立显示，不合并成一个总评分。

批量排程复用现有任务表单，只填写一次动作、日期及巡查附加措施，再一次确认。适用于巡查、系统灌溉、人工补水、喷施、维修和经理巡查；支持今天或同一个未来日期。经理巡查依然每个单元消耗 2 点注意力，普通批量排程不额外扣注意力。复杂判断和团队/助手建议继续按具体问题处理。

为保持简单且可预期，批量确认采用以下规则：

- 逐单元计算并汇总劳动力、水量、费用和注意力，连同该日已有预约一起校验；不能只检查每个任务单独是否放得下。
- 保留“生产单元＋日期＋动作类型”的唯一性，巡查组合中的附加动作也参与重复检查。
- 若任一单元重复或有资源冲突，整批先不创建任务，明确列出对应单元、动作或总资源缺口。玩家可移出冲突单元、查看已有任务、改期或取消后再确认，不静默跳过，也不留下未说明的部分成功。
- 确认成功后按单元生成任务与历史，汇总提示成功数量，并展示每个单元的安排；执行结果、改期和取消仍可逐单元追踪。
- 同一移动传感器只能迁往一个目标。传感器迁移及含迁移的组合需要单独指定来源和目标，不把一个传感器复制到多个单元；多选时明确提示需要逐项安排。

流程示例：勾选 PU-04、PU-05、PU-08 → 选择今天巡查 → 显示总劳动力 3 → 一次确认 → 看见三条对应任务。无需三次跳转并重填日期和动作。

验收：只在表格页即可选择并操作；表格与单元视图可同时选择多个单元并执行相同作业；切换视图不丢选择；批量资源合计、重复限制、经理注意力、传感器唯一性与逐单元历史均符合现有规则。

### 第三批：收敛决策与资源表达

**C1. 相同意思只保留一个入口，不让玩家先理解两套工作流。**

实际问题：决策卡同时有“交给团队”和“请下属提出方案”；场景委派次日汇报，而单元助手可即时给建议。03-14 单元面板显示了委派按钮，点击后只得到“普通决策可以直接排程”，玩家在点击前不知道该入口不适用。03-16 的建议位于历史列表顶部，但页面切换后停留在列表底部，需要重新寻找。

建议每个复杂问题统一为“经理判断 / 团队建议 / 智能助手建议”。选择后就地显示当前状态；需要等待时直接写“明早汇报”，即时建议则当场显示接受/拒绝与资源摘要。普通问题提供直接排程入口，复杂委派入口在不适用时不出现。

保留原有建议生成与送达规则，保留接受/拒绝，不新增修改建议的流程。注意力不足时，团队和助手仍可用。

验收：玩家不用读玩法简介中的例外说明，也知道建议现在可接受还是要等明天；每个问题只有一个团队委派入口。

**C2. 资源校验、采购与结果采用可对照的口径。**

实际问题：03-02 普通灌溉 20 m³ 使用劳动力 1、费用 ¥65；03-05 场景建议灌溉同为 20 m³，却使用劳动力 4、费用 ¥260。普通排程以劳动力点显示，任务卡又改成人员日；接受建议前不容易看清剩余容量。03-22 缺水时采购入口在另一个页面。

建议确认、任务列表和实际结果统一优先显示劳动力点、水量、费用、日期；人员日作为需要时展开的换算。核对两个入口是否确有覆盖范围、时长或执行人员差异：有差异则在选择前说明；没有差异则共享同一套资源报价与校验。不能未经核实就把所有成本改成一样。

缺水或容量冲突时在当前卡内显示缺口，并链接已有采购、改期或取消操作。采购仍保留付款确认；采购完成返回原任务，保留已填参数，不自动执行。

验收：同一任务在确认前后的资源口径一致；接受建议前看得见总消耗；解决冲突后无需重填整个安排。

**C3. 季末复盘默认落在历史，而不是空白的未来窗口。**

季末观察日历从 03-29 开始，但试玩日期已经结束，界面只剩生产单元行而没有日期列。建议季末默认显示最后七个经营日；结束页面不再说“推进一天等待新的报告”，也不显示“当前可排程今天/未来”的操作说明。

复盘使用已有结果，突出少数“问题→选择→行动→结果”的链条，再展开完整审计。团队/助手选择应显示自动理由，经理未填写可选理由不应看起来像流程没做完。

验收：经营结束后，一次进入复盘就能回看最后一周与关键行动；不会误以为还能继续当前一轮。

## 4. 建议的一天

```text
进入早会 / 今日工作
  → 看昨日结果和今日变化
  → 从对应事项或单元打开任务，核对并确认
    （多个单元做同样工作时，多选后填写一次并确认）
  → 当前任务就地显示，未来安排按需展开
  → 开始执行
  → 自动停在日终结果：完成、受阻、资源变化、预计影响
  → 玩家查看后进入次日早会
```

普通日围绕一个工作页完成主要流程；总览、完整日历、知识与历史仍可随时查看。缩减的是寻找入口和重复确认，不替玩家决定应该保护哪块地。

## 5. 后续验收顺序

1. Pages 路由下走通重复任务查看、改期、取消；完整 28 天存档与恢复；中文水量统一为“立方米”，检查中英文单位、完整句子、分隔符和数值格式。
2. 新手从早会辨认未知/陈旧信息，在同一上下文中安排当天组合任务与未来任务，立即看见成功状态；表格下方可直接选单元，表格和单元视图可多选批量排程，核对资源合计、重复冲突、视图切换和逐单元结果。
3. 一次开始执行后进入结果；巡查同时呈现作物/设备观察，灌溉区分预计与次日观测；不开放中途排程。
4. 复杂问题中走通经理、团队、助手入口，明确等待与批准；注意力为零时仍可排普通任务。
5. 资源不足时就地看缺口，采购/改期后回到原安排；相同任务跨入口核对资源消耗。
6. 使用本轮规模的任务和历史，检查当前工作的位置、点击数、跳转和季末日历；再请实际新玩家做一轮对照。

只在这些流程顺畅后再考虑更多作物或更复杂模型。本次没有修改应用源码、提交、推送或部署。
