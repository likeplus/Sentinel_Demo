# Phase 2：农场经理主工作台

本轮将已经合并到 main 的 Phase 2 反馈版（基线 `5a71f17`、PR #7）重组为一个主工作台。目标是让玩家沿着“看状态与证据 → 安排工作 → 执行 → 对照结果 → 次日调整”完成一天，减少页面跳转和重复填写。保留原场景、时间规则、原演示应用、经济记录、委派机制与历史链。

## 1. 导航与信息位置

| 位置 | 内容 | 操作与边界 |
| --- | --- | --- |
| 农场总览左栏 | 天气、风险与信息缺口、当天送达报告、状态表／空间视图、可选日历、单元证据、水分趋势 | 看已经获得的信息；选择一个或多个单元 |
| 农场总览右栏 | 待处理决策入口、当天／未来任务表单、容量报价、当前与未来任务、执行结算 | 早会排程；执行后优先显示结算 |
| 决策中心 | 原场景复杂决策、经理／团队／助手判断、接受或拒绝、决策历史 | 普通作业不必经过决策中心 |
| 经营管理 | 人员与资源、资金流水、存档、期末复盘、传感器资产清单 | 移动传感器从资产页进入正式迁移排程 |
| 玩法简介 | 模块化玩法卡片 | 解释实际已实现的规则 |
| 作物知识 | 作物百科与阶段卡片；单元上下文跳转 | 阶段依据玩家已收到的报告；未知不推断 |

原来的“今日工作／作业排程／生产单元”导航合并到农场总览。旧浏览器偏好中的三个标识自动映射到新工作台。`#/game` 路由保留，不用作业 ID 覆盖页面路由。

## 2. 状态与证据的含义

状态表取消独立的信息新鲜度列，在水分、病虫害迹象、设备各自下面显示“信息更新：当天／几天前／暂无信息”。

- **水分胁迫**：当前估计及来源。估计可信度、范围、预计影响在单元详情查看。
- **病虫害迹象**：最近有效巡查实际记录的迹象，不是整株健康评分。水分胁迫高而未见病虫害并不矛盾，也不自动证明缺水的具体原因。
- **巡查可信度**：最近有效巡查报告的可靠度。传感器刷新不能提高这份报告的可信度。
- **暂无巡查**：没有报告；不能显示为健康或用 0% 代替缺失。
- **未单独记录**：旧报告只有泛化的作物正常字段，没有独立病虫害记录；保留原文，不倒推不存在的证据。
- **设备状态与长期可靠度**：继续分开显示。设备信息的巡查日期不会被浇水动作重写。

一次有效巡查同步产生水分、作物与设备信息。此后传感器可独立刷新水分信息，两类日期可以不同。作业完成不等于风险解除；预计改善与后续观测确认继续分开。

## 3. 排程与资源

选择单元自动成为右侧排程对象。表格、表格下方选择区与地图共享多选状态，每个单元生成独立可追溯任务。批量排程全部成功或全部不创建。

切换单元、查看资产或作物知识不会重置日期、作业、班组与理由；跨到新的一天会重置为当日草稿。草稿只保留在当前会话，未提交的内容不写入游戏存档。

表单采用两列网格，附加作业采用对齐的勾选卡片。容量表显示“可用／已排／本次需求／排程后剩余”；预计费用单列。水量已经扣除全部未执行预约，说明文字避免玩家再次相减。

保留以下硬规则：

1. 只有早会能排程、取消或改期，支持当天和未来日期。
2. 早会固定扣 1 注意力，普通排程不额外扣点。
3. 经理巡查预留 2 注意力、0 劳动力，附加现场工作正常消耗劳动力。
4. 单元＋日期＋作业类型唯一；组合任务中的每个动作都参与去重。
5. 取消释放预约，不产生观测；改期失败保留原任务。
6. 执行后直接停在日终复盘，日期不提前；再点击才进入次日早会。
7. 费用与库存按实际执行记账，不因重载或重复提交多扣。

本轮还修正了一个原有资源兼容性缺口：组合任务不再统一忽略不兼容错误。班组需要支持它实际执行的全部现场动作；水库只核对用水动作；灌溉设备只核对灌溉。`repair` 对旧 `maintenance` 能力保留兼容。预览、创建、执行遵循同一检查口径。执行前检查只使用临时资源视图：任务因资源受阻时，维修效果、观测、用水和费用均不得提前发生。

## 4. 日历、趋势与结果

“显示日历”为可记忆的展示偏好，日期列直接延伸在同一张生产单元状态表右侧。生产单元名称固定，表格内部横向滚动。日历可切换作业排程与观察记录，每格可查看来源、采样时间、结果、可信度、发现和关联作业。观测按观测日期归位，不把迟到报告改成送达当天的观测。异常判断只对水分变量应用水分阈值，不把温度等其他数值当作胁迫。

水分趋势默认跟随当前单元或多选，也可查看全场或指定单元。未知不绘制，颜色按单元身份保持稳定，阴影仍是现有中等复杂度的不确定范围。

执行后隐藏排程编辑区并优先显示结算表；待执行与未来任务仍可查看。结算使用实际劳动力、实际扣除库存水量、实际费用与受阻／失败状态，保留预计影响、详细巡查和执行记录。已完成任务详情按需展开，避免长期试玩时持续渲染全部历史卡片。

## 5. 与真实性及扩展方向的关系

本轮是界面与相关正确性工作，**没有实现持续策略、日内自动灌溉、过湿／盐分／pH、自由配肥、经营目标评分或数据库**。当前系统灌溉仍表示一次作业，玩法卡片明确说明这一点，不把任务换个名字当作持续策略。

后续右栏可接入“持续策略／偏差处理／临时作业”，但持续策略应有独立身份、作用对象、阶段目标、授权范围、有效期与复核条件，不能每天克隆一批任务来伪装持续运行。

| 当前约束 | 后续演进方向 |
| --- | --- |
| UI 只读取安全的玩家视图，浏览不改变随机数／仿真状态 | 决策仍只使用当时可用证据，隐藏真实状态由仿真读取 |
| 界面投影与渲染分离，单位数量、品种来自配置 | 变量注册与单位、对象、缺失语义契约 |
| 品种键改为作物包＋品种组合标识 | 避免不同作物同名品种覆盖；并不声称已支持混种完整业务 |
| 巡查／水分可信度／时间分别保留 | 观测对象进一步区分地块、作物批次、设备 |
| 资源兼容性按参与动作核对 | 完整 ActionDefinition 与能力需求契约 |
| 原存档数据结构不变，旧泛化报告诚实显示 | 模块级版本、迁移与独立随机流需单独设计和验证 |
| 作物知识仍为可扩展卡片 | 新作物阶段和农艺差异由作物包定义 |

下一轮先明确最小变量、观测对象与措施契约，再完成蓝莓“持续供水—日内执行—干湿双向后果—少量异常卡—因果复盘”闭环。供水和营养调整必须分开，自动化权限由设备条件决定。第二步待确认信息见 [持续策略问题清单](12_Blueberry_Persistent_Policy_Questions.md)。

## 6. 验收入口

- `npm test`：原核心回归及工作台证据、兼容性、配置测试。
- `npm run test:game:workspace`：真实控件操作，草稿保留、表格／地图多选、日历、当天／未来工作、结算、迁移、偏好兼容。
- `npm run test:acceptance`：完整 28 天原内容与 112 作业高频巡查、旧应用路由。
- `npm run test:game:locale`、`:review`、`:onboarding`：双语、复盘／阶段知识、说明卡。
- `npm run build:pages && npm run test:pages`：严格静态服务器验证部署产物、刷新、资源、旧路由。

最终实测结果见 [工作台验收记录](validation/workspace-results.md)。本文件是下一次修改的设计基准；历史设计文档作为版本记录保留。
